# Little Smalltalk

Little Smalltalk 6.0.0 (based on 4.7 by Budd / Valencia / Hayes; the version is set in `project()` in `CMakeLists.txt`): a small bytecode Smalltalk VM in C++ (`lst`) that can also bootstrap: compile Smalltalk source into an image (`lst -o`), and one image: the command-line REPL. See `README.md` for the changes compared to the original repository and how to use it, and `TODO.md` for planned work.

**No method source in the image**: a `Method` has no `text` (the fields are name, byteCodes, literals, stackSize, temporarySize, class), so there is nothing to show, edit or file out: the method editor (primitive 105, `String>>edit`, `Class>>addMethod`/`editMethod:`), `Class>>view:`/`viewMethod:` and the file-out methods (`Class>>fileOutSource`, `File>>writeImageSource`...) were removed on purpose. The `.st` files are the source.

**Keep it basic: REPL only.** The original web IDE / class browser (Smalltalk `webide.st`, `webui/classbrowser.st`, image `lst_webide.img`) and the VM support for it (TCP socket primitive 200, URL encoding primitives 151/152, Winsock) were removed on purpose. Don't add networking, HTML or web UI code back.

The code is C++20, organized in classes; the method bodies are mostly still the original C code (see "C++ status"). It must build on **Windows** (MSVC), **Linux** (GCC/Clang) and **macOS** (Clang). Keep platform-specific code in `src/platform.h` (and `#ifdef _WIN32` blocks next to it); don't scatter `<unistd.h>`, `<io.h>`, `bzero`/`bcopy`, `gettimeofday` etc. through the sources.

## Layout

- `src/`: all C++ sources, the VM and the compiler that bootstraps an image (the former `bootstrap` executable was merged into `lst`; one piece of code per job: there is no second copy of symbol compares, special objects, allocation or `main`). One class per `.h`/`.cpp` pair (`CompiledMethod` and `CompiledLiteral` have no functions, so no `.cpp`); no global state
  - `main.cpp`: `lst` entry point: `main` only makes an `App` and calls `start` with the command line as a `std::vector<std::string>` (the program name first)
  - `App`: the `lst` program. `start` keeps the strings (and `const char*`s into them for `VirtualMachine::setArguments`, primitive 170), `parseArguments` (args: `[-v] [image]` or `[-v] -o outputfile [sourcefolder...]`, else `usage`), then makes a `VirtualMachine` and calls `buildImage` (`-o`) or `runImage`; with `-o outputfile` it compiles the source folders (in order, default `Smalltalk/System`, relative to the working directory; their order does not change the image) into the image `outputfile` (`buildImage`), then loads the image (`outputfile`, or else `image`, default `lst.img`; more than one name without `-o` is a usage error) and runs it. The REPL reads its commands from standard input (there is no command file option: `-x` was removed on purpose; a program is a class `Main` with `start`). There are no memory size options (`-s` and `-d` were removed: both the static and the dynamic space grow by themselves). There is no debug option (`-g` and `Log::info` were removed on purpose; don't add debug logging back)
  - `VirtualMachine`: owns and connects the parts (declared in construction order): `ObjectMemory`, `SpecialObjects`, `Diagnostics`, `Primitives`, `Interpreter`; sets the collector's `afterCollect` callback to flush the method cache. `buildImage( sources, image )` (a `CompiledImage` on its `ObjectMemory` and a `Compiler`; writes the file, then `releaseStatic`), `loadImage` (`findInitialMethod`: `Main>>start` if the image has a class `Main` that understands `#start`, looked up through its superclasses with `findMethod`; else `Shell>>start`), `run` (root process for the initial method; it prints only how it ended when that was not a normal return, no statistics; for `Main>>start` the receiver is a new `Main` instance, `Shell>>start` runs without one, as it always did)
  - `Object.h`/`Object.cpp`: the object layout classes `Object`, `ByteObject`, `MObject` (the GC's view: the class is `data[ 0 ]`) with header accessors (`size()`, `setSize()`, `isBinary()`, `bytePtr()`..., replacing the old `SIZE`/`bytePtr` macros), `Object::toWords`/`wordsUp`/`wordsDown`, `BytesPerWord`, `SmallInt` (`is`, `fits`, `value`, `make`: the tagged integers, never call a member function on one), and `Symbol::compare` (the one byte-wise symbol comparison, like `strcmp`, for symbol/symbol, C string/symbol and raw bytes: method lookup, `dictLookup`, the `CompiledImage`'s sorted dictionaries and symbol tree). Plain data on purpose (`class` with all fields public, no constructors, no virtual functions): the collector moves them as raw memory, and the three must keep the same header layout
  - `ObjectLayout.h`: class `ObjectLayout`, the field offsets and sizes as `static constexpr` members (`ObjectLayout::nameInClass`, `ObjectLayout::methodInContext`, `ObjectLayout::classSize`...), always used qualified; `OpCodes.h`: class `OpCodes`, the bytecodes as `static constexpr` members (`OpCodes::sendMessage`, `OpCodes::pushBlock`...), the special operations (`OpCodes::stackReturn`...), the constants of `pushConstant` (`OpCodes::nilConstant`...) and the codes `execute` returns (`OpCodes::returnError`...); always used qualified, so they don't clash with the `Interpreter` methods of the same name
  - `ObjectMemory`: Baker two-space GC whose dynamic space grows: it starts at `defaultDynamicSize` (a `constexpr`, units of `sizeof( Object )`, 2 words), and when a collection leaves less than a quarter free (or not enough for the object), `grow` replaces both spaces by larger ones (twice the size, or more for a large object) and copies the live objects there (`collect` and `grow` share `moveLiveObjects`); `reserve( bytes )` makes the empty space big enough before an image is read (`VirtualMachine::loadImage` reserves 16 times the file size: the image reader must not collect, its objects are not reachable yet); `allocate`, `allocateBytes`, `allocateStatic` (the static space: never collected, objects never move; only the `CompiledImage` being compiled uses it; it is a list of blocks (`staticBlocks`): the first of `defaultStaticSize` (a `constexpr`), and when the last is full `addStaticBlock` adds one of twice the size (or what a large object needs); old blocks stay where they are, because the compiler keeps raw pointers to static objects; `releaseStatic` keeps only the first block, empty; `exchangeObjects` walks every block) and `releaseStatic`, the root stack (`pushRoot`/`popRoot`/`peekRoot( depth )`), `addStaticRoot`, `collect`, `isDynamic`, `exchangeObjects`, statistics
  - `SpecialObjects`: nil, true, false, the globals dictionary, the classes the VM uses and the special symbols, as public members that are registered as static roots (the GC updates them: never keep a copy across an allocation); the compiler's `CompiledImage` keeps the ones it makes in its own `SpecialObjects` (not roots). `findInGlobals`, `lookupGlobal`, `dictLookup`, `classOf` (was `CLASS`), `notNil`
  - `Interpreter`: `execute` (the bytecode loop: decodes an instruction and calls the method for it: `pushInstance`, `pushBlock`, `sendMessage`, `sendBinary`, `doPrimitive`, `doSpecial`...; `send`/`sendToClass` look a method up and start its context, `doReturn`/`returnToContext` return to the previous one; the methods that can end the process return its `OpCodes::return...` code, else `continueExecution`; a jump target in the bytecodes is read with `codeValue()`, `codeValueSize` bytes), the registers of the running process are members (`context`, `stack`, `stackTop`, `bytePointer`...; primitive 6 runs another process in them, its own context is loaded again afterwards by `doReturn`); `doPrimitive` dispatches to one method per primitive the interpreter does itself (`objectIdentity`, `arrayAtPut`, `invokeBlock`, `smallIntAdd`... `integerOperation` for 25-31, `callPrimitive` for the `Primitives` class), each returning `primitiveSucceeded`, `primitiveFailed` (then `failPrimitive()`), or a status that ends the bytecode (`continueExecution` after `invokeBlock`, `OpCodes::returnError`); two SmallInt arguments are popped with `popTwoSmallInts( high, low )`; there is no `goto` and no macro in the interpreter. This is about 20% slower than the single function with locals it was, on purpose: readability first, it is an instructional project. `lookupMethod`, `bulkReplace`; owns the `MethodCache` (`find`, `store`, `flush`, hit/miss counts)
  - `Primitives`: `call( number, arguments, failed )` for the primitives the interpreter does not do itself; it only dispatches to one method per primitive (`openFile`, `readCharacter`... `compareSymbols`, all `( arguments, failed )`; `fileAt` checks a file number) (files 100-108, substring match 150, log/timestamps 160/161, argv 170, compile a method 180: a `RuntimeCompiler`, compare a Symbol with a Symbol or String by its bytes 181: `Symbol::compare`, for `Symbol>>compare:`, which `Symbol>><` and `=` use (they fall back to comparing `printString`s when it fails); so Smalltalk and the VM sort and search symbols the same way), the open files, `newLInteger`/`doInteger` (64-bit Integers)
  - `Image`: an image file (the former `ImageReader`, `ImageWriter` and `ImageFormat` in one class). `Image( memory, objects )`; `read( file )` (`VirtualMachine::loadImage`; the indirection table is in the unused space) and `write( file, root )` (primitive 104 and `CompiledImage::writeImage`; its own table: an `unordered_map` from object to its index, the order of writing; no limit on the number of objects); the format constants (header `lst!` + version byte, tags: `Image::objectType`...). Only image version 6 (`Image::imageVersion`): the older formats (no header, raw memory dump) were removed on purpose. Files stay C `FILE*`s
  - `Log`: `Log::error( fmt, ... )` (prints, then exits), printf-style, the message starting with the caller's function name and line. No macros: the format string converts to a `Format` (a small class before `Log` in `Log.h`), whose constructor's default argument `std::source_location::current()` is evaluated at the call site. `error` is a small variadic template in `Log.h` (templates must be in the header) that passes on to the C varargs `errorAt` in `Log.cpp`; there is no debug flag or trace output (`Log::debugging`, the interpreter's `TRACE` build, primitive 18 and `Object>>debug` were removed on purpose); `Diagnostics`: `backTrace`, `dumpObject`, `dumpMethod`, `dumpDictKeys`
  - `platform.h`: POSIX vs Windows shims (`alloca`, `lstTimeUsec`)
  - `version.h.in`: CMake generates `version.h` (git-ignored) from it
- The compiler (in `src/`): one compiler for both jobs. `lst -o` uses it through `VirtualMachine::buildImage` (`Compiler`), and the running image through primitive 180 (`RuntimeCompiler`) for everything it compiles: the REPL's expressions (`String>>doIt`), `File fileIn` and `Class>>addMethod:` all go through `Class>>parseMethod:`. There is no compiler written in Smalltalk any more (the Smalltalk `Parser`, `Encoder` and `ParserNode` classes were removed on purpose; don't add them back):
  - `CompiledImage`: the image being compiled (not the image file: that is `Image`). Constructed on the VM's `ObjectMemory`; the constructor does the big bang (first classes). Globals: the global names and objects (`addGlobal`, `lookupGlobal`; at the end `fillGlobalsDictionary` and `checkGlobals`). nil, true, false, the VM classes and the globals dictionary are in its `SpecialObjects objects` member (`image.nil()`); the other big-bang classes are locals of `bigBang`. Objects: allocates image objects in the static space (`memory.allocateStatic`; `alloc`, `allocBytes`, `newSymbol`, `newClass`, `newArray`...), `dictionaryInsert`, and the symbol table (`buildSymbolTree`). `writeImage` adds the special symbols, does the symbol/global fix-ups and writes the file with `Image`. `alloc` sets `objectClass` to `nullptr`: that is how `checkGlobals` finds classes that were never defined
  - `Parser`: the source file (`open`), the text buffer, the cursor `cursor` and the token buffer, all private. Reading: `nextLine`, `readMethodText`, `skipSpaces`, `readIdentifier`, `readBinary`, `readInteger` (64-bit), `readString` (`''` is a quote), `readSymbol`/`readSymbolName` (names, keywords like `at:put:`, binary selectors)..., `setText` (a method text from the runtime compiler), `parseError`. `parseError` throws a `CompileError` (a struct in `Parser.h`: the message and `textLine()`, the line of the last token in the text); it never exits: the `Compiler` turns it into `Log::error` with the file and line, the `RuntimeCompiler` into an error String. The cursor: `current()`, `peek( offset )`, `advance()`, `position()`/`setPosition()` (an index into the text). Read only: `token()`, `text()`, `line()` (the file line)
  - `Compiler`: does all the compiling of the source files into a `CompiledImage`, with its own `Parser` member, in **two phases** (`compileFolders` lists the `*.st` files of each source folder and its subfolders (`recursive_directory_iterator`), the folders in the order given and the files of a folder sorted by path; an unknown or empty folder is an error; then `compileFiles` runs phase 1, then phase 2 once; `Parser::open` restarts the line count for each file). **Phase 1** (`compileSource`) is the line loop over one source (`+` class definition, `=` class method, `!` instance method) and makes no image objects; it reads all files twice: first only the class definitions (methods skipped with `readMethodText`), then `checkClasses` (every superclass exists; `addSubclasses` sets `hierarchyOrder`: depth first, the subclasses of a class sorted by name; a class whose superclass is not compiled is a root), then only the methods, so a method can use any class of any file: `compileClass()` parses a `+Super subclass: #Name variables: #( ) classVariables: #( )` line (`compileClassDefinition`; empty names are rejected; `compileVariableNames` splits the variable lists) into a `CompiledClass` in `classes`; `compileMethodDefinition( classSide )` finds the class and compiles the method with a `MethodCompiler`, giving it the instance variables from the `CompiledClass` chain (`instanceVariablesOf`, `superclassOf`: a metaclass's parent is the superclass's metaclass, MetaObject's is Class) and `isGlobal` (a global name must be in the image, the big bang, or be a class compiled so far); the `CompiledMethod` goes into the class's `instanceMethods` or `classMethods`. **Phase 2** (`generateImage`) makes the objects: `generateClass` for every class in `hierarchyOrder`, then `generateMethod` class by class in that order, the class methods first, each side in source order (the order of the old single `lst.st`, so the split sources give the same image); `buildVariableArray` and `buildLiteralArray` make the symbols and literals. Keep that order, and within a method the selector before the literals: the symbol table is a tree built in symbol creation order, so a different order changes the image. `currentMethod.code` holds the bytecodes being generated; `variableTop()` is the number of method and block variables in scope (`OpCodes::pushTemporary`, `OpCodes::assignTemporary` and `temporarySizeInMethod` keep their VM names). `buildLiteral` makes one literal, a literal array recursively. An integer literal outside the `int` range is an error (inside it, `SmallInt::make` as the image always had it)
  - `MethodCompiler`: the method parser and code generator, shared by the `Compiler` and the `RuntimeCompiler`. Made with the `Parser` (cursor at the start of the method), the instance variable names (all of them, superclass variables first; looked up from the end) and an `isGlobal` function; `compile()` returns the `CompiledMethod` (selector, `code`, `literals`, `variableCount` as the high-water mark of method and block variables in scope) or throws a `CompileError`. It makes no objects: literals are only described (`addIntegerLiteral`, `addSymbolLiteral`, `addGlobalLiteral`..., `readLiteralArray` for `#( 1 $a 'b' foo #( 2 ) )`). The names in scope (`argumentNames`, `variableNames`; `nameTerm` and `compileAssignment` look a variable up from the innermost one, so a block argument hides a method variable of the same name) and the code generation flags (`superMessage`, `returnOperation`, `blockbackup`) are members; `resetMethod()` empties them. `currentMethod.code` holds the bytecodes being generated; `variableTop()` is the number of method and block variables in scope. It only reads the source through the `Parser`'s functions; saved source positions (`savedPosition`, `savestart`, `blockbackup`, which is -1 when there is no block to loop over) are `int` positions. Names are `std::string`s (no fixed buffers: the REPL compiles whatever is typed)
  - `RuntimeCompiler`: primitive 180 (`Class>>compile:variables:`, called by `Class>>parseMethod:`): the method text and the instance variable names (Symbols) in, a `MethodCompiler` compiles it, and the result is built in the dynamic memory: an Array of the selector (a String), the bytecodes (a ByteArray), the literals (an Array of `#( kind value )` pairs: 1 an object, 2 a symbol as a String, 3 a literal array as an Array of pairs), the stack size and the number of temporaries; or, for a syntax error, a String (`near line 2: unknown identifier foo`). The Smalltalk side makes the symbols (`asSymbol`: the symbol table is Smalltalk's `Symbol` class variable) and the `Method` (`Class>>compiledLiterals:`). Every object it allocates gets its class and nil fields at once, and intermediate objects are on the root stack (allocating can collect garbage)
  - `Bytecode`: the bytecodes of one method (a `std::vector<uint8_t>`): `genByte`, `genVal`, `genInstruction`, `genValPos` (patches a value in place, for jump targets), `byteTop()` (the current code position), `byteCodes()`, `clear()`, and `buildByteArray( image )` (phase 2)
  - `CompiledClass`: data of one class from phase 1: the four strings of its definition line (superclass, class name, instance and class variable lists), the variable names (`instanceVariableNames`, `classVariableNames`), its methods (`instanceMethods`, `classMethods`), and the objects phase 2 builds (`superclass`, `metaclass`, `instanceClass`). No logic beyond `metaclassName()`. A class defined again replaces the earlier definition (its methods are compiled after all definitions, so they are kept)
  - `CompiledMethod` (header only): data of one method from phase 1: `selector`, `Bytecode code`, `literals` (`CompiledLiteral`s), `variableCount`, `stackSize`
  - `CompiledLiteral` (header only): one literal of a `CompiledMethod`: its `kind` (integer, string, symbol, char, global name or literal array) with a `value` (64-bit), `text` or `elements`; phase 2 (`buildLiteral`) or the `RuntimeCompiler` makes the object
  - Dependencies point one way: `Compiler` → `CompiledImage`, `Compiler` → `MethodCompiler` → `Parser`, `Compiler` → `CompiledClass` → `CompiledMethod` → `CompiledLiteral`, `CompiledMethod` → `Bytecode` → `CompiledImage` → `Image`; `Primitives` → `RuntimeCompiler` → `MethodCompiler`
  - After the image file is written, the VM loads it like any other image; it does not run the compiled objects themselves (the writer writes references to the root, the globals dictionary, as nil, so a loaded image differs from them). Then the static space is emptied
- `Smalltalk/`: Smalltalk sources. `System/` builds the REPL image: one file per class, named after the class (`Object.st`, `Shell.st`...), with its definition line, class methods and instance methods; `Magnitude` and its subclasses except `Collection` (Association, Char, Number, Integer, SmallInt, Symbol) are in `System/Magnitude/`, `Collection` and its subclasses (Array, ByteArray, OrderedArray, String, Dictionary, Interval, List, StringBuffer, Set, IdentitySet, Tree) and `Link` and `Node` (Object subclasses: the links of a List, the nodes of a Tree) in `System/Collection/`, `Object`, `Undefined`, `Boolean`, `True`, `False` and `Block` in `System/Base/`, `Class`, `Method`, `Context` and `Test` (the unit test superclass, in every image so that any program can have tests) in `System/Reflection/`, `Application`, `File`, `Process` and `Shell` in `System/OS/` (no class files in `System/` itself); `Examples/` are extras not used by the build. `Test/`: the unit tests of the system classes (the class `Test` itself is in `System/Reflection/`): one `Test<Name>.st` per class of `System/` (`TestArray` tests `Array`...), in the subfolder of the same name as the class's own (`Test/Collection/TestArray.st` for `System/Collection/Array.st`), and a `Main.st` that runs `Test all`. A test class subclasses `Test`; its test methods are the methods whose name starts with `test` and has no arguments (`test`, or `testAccess`, `testCopying`... for several groups); a test checks with `self assert: aBoolean`. `Test all` runs the test methods of all subclasses (in name order), each in a `Process` of its own (`Context>>perform:withArguments:`), so an error ends only that test; it reports every failed assert (`TestList>>testRemoving: assert 3 failed`) and error, and at the end `All N tests passed (M asserts)` or how many failed. The counts are class variables of `Test` (`Test assert:` keeps them; the instance `assert:` calls it). The bootstrap compiler has no 64-bit literals, so the tests make those with `doIt`. When a test fails because of a bug in a system class, keep the test: fix the class. `Examples/`: example programs in fileIn format, each in its own source folder (`Concordance/`, `Palindrome/`, `Queen/`, `Primes/`, with `<Name>.st`; `While/` has no classes of its own), extracted from the 1994 shell archive `Tests.st`. **Startup**: an image with a class `Main` that understands `#start` runs `Main new start` instead of the REPL, and `lst` exits when it returns; without `Main` the VM starts the REPL. Every example folder has a `Main.st` (`+Application subclass: #Main ...` with `!Main start`), so `lst -o x.img Smalltalk/System Smalltalk/Examples/<Name>` builds the program's image and `lst x.img` runs it. Concordance reads its text from standard input: `... < Smalltalk/Examples/Concordance/Input.txt` (not `.st`, or `-o` would compile it). Every example folder has `build.sh` (`lst -o lst.img ../../System .`: the image `lst.img` in the example's folder, git-ignored) and `start.sh` (runs it; Concordance's reads `Input.txt` when standard input is a terminal); each script is self-contained and runs `../../../bin/lst` (a relative path; Git Bash finds `lst.exe`). Or load it into a running image with `File fileIn: 'Smalltalk/Examples/<Name>/<Name>.st'`. Comments are lines starting with `"` (the bootstrap compiler rejects other lines it doesn't know), class definitions need the full `subclass:variables:classVariables:` form
- `bin/`: what the build makes (git-ignored, nothing committed): the image `lst.img` (the `baseimage` step) and a copy of the executable (a `POST_BUILD` step in `CMakeLists.txt`, so the configuration built last is the one there): the examples' scripts run it
- `cmake/baseimage.cmake`: the `baseimage` step: runs `lst -v -o bin/lst.img Smalltalk/System`; `-o` only writes the image, it doesn't run it (a build must never wait for input)
- `build/`: CMake output (git-ignored); the executable goes to `build/Debug/` and `build/Release/` (and is copied to `bin/`)
- `build.sh [debug|release]`: builds `lst` with CMake (Release by default), choosing the presets from `uname` (`msvc`/`debug`/`release` on Windows, with the cmake bundled with VS when `cmake` is not on PATH; `linux`/`linux-...`; `macos`/`macos-...`); that build also makes `bin/lst.img` (the `baseimage` step) and copies `lst` to `bin/`. Then it builds `bin/test.img` (`Smalltalk/System Smalltalk/Test`) and runs the unit tests
- `start.sh`: starts the REPL: `bin/lst bin/lst.img`
- `clean.sh`: removes `build/`, `out/`, `.vs/`, the generated `version.h`, the copy of `lst` and all `*.img` files in `bin/` and the example folders, and stray compiler output
- `zipit.sh`: zips the tree to `../LittleSmalltalk.zip`, leaving out the same build artifacts (needs Info-ZIP `zip`)

All scripts are **bash** (`.sh`, run from Git Bash on Windows), never `.cmd`/`.bat`/`.ps1`. Each one `cd`s to its own folder first, and its exclusion list matches `.gitignore`.

## Build

**CMake** (`CMakeLists.txt` + `CMakePresets.json`), used by VS Code. There is no Visual Studio project.

- Targets: `lst`, and the custom target `baseimage` (built by default, depends on `lst`), which runs `lst -o` on the source folder `Smalltalk/System` (through `cmake/baseimage.cmake`) to produce `bin/lst.img`.
- Each preset has a host condition, so only the right one shows up:
  - Windows: configure preset `msvc` (**Visual Studio 18 2026** generator, x64), build presets `debug`/`release`. The generator finds MSVC by itself; no developer prompt needed.
  - Linux: configure preset `linux` (**Ninja Multi-Config**, needs `ninja`), build presets `linux-debug`/`linux-release`.
  - macOS: configure preset `macos` (Ninja Multi-Config), build presets `macos-debug`/`macos-release`.
- In VS Code, CMake Tools configures the project when it opens. `.vscode/settings.json` makes CMake Tools the IntelliSense configuration provider (with `C_Cpp.default.cppStandard` `c++20` as fallback), so IntelliSense knows the C++20 flags; without it, C++20 names like `std::string::starts_with` show up red although they compile. F7 builds (and bootstraps `bin/lst.img`); F5 uses `.vscode/launch.json`: two configs for Windows (`cppvsdbg`, `build/Debug/lst.exe`) the same two for Linux (`cppdbg` with gdb, `build/Debug/lst`; built with clang or gcc) and for macOS (`cppdbg` with lldb, `build/Debug/lst`; its debugger cannot use the integrated terminal: the unit test output is in the Debug Console, and the shell opens an external Terminal window, because the REPL needs standard input), all with the top folder as working folder (build Debug first), each with a `preLaunchTask` from `.vscode/tasks.json` that builds the image first, after the task "lst: build debug" (`cmake --build` with the Debug preset of the host: `debug`, `linux-debug` or `macos-debug`; on Windows with the cmake bundled with VS), so F5 always runs an up-to-date VM (the image tasks run `lst.exe`, with `linux` and `osx` overrides for `lst`; `-o` only writes an image, so building and running are two steps; `tasks.json` is versioned):
  - "lst: build image and run unit tests (Windows)": task "lst: build unit test image" (`-o bin/test.img Smalltalk/System Smalltalk/Test`), then runs `bin/test.img`: `Test all`, ending with `All N tests passed`
  - "lst: build image and run shell (Windows)": task "lst: build shell image" (`-o bin/lst.img Smalltalk/System`), then runs it: the REPL
  - the shell config overwrites `bin/lst.img` (the default image name), also the one the build (F7) made; the unit test config has its own `bin/test.img` (both git-ignored)
- From a Windows terminal, `cmake` is **not on PATH**; use the copy bundled with VS:
  ```
  "C:/Program Files/Microsoft Visual Studio/18/Community/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/cmake.exe" --preset msvc
  ... --build --preset debug     # or: --preset release
  ```
- On Linux/macOS: `cmake --preset linux` and `cmake --build --preset linux-debug` (or the `macos` equivalents).

Compiler settings: C++20, no extensions. MSVC: `/W3 /permissive- /Zc:__cplusplus /utf-8`, `/JMC` in Debug, `_CRT_SECURE_NO_WARNINGS`, `_CRT_NONSTDC_NO_DEPRECATE`. GCC/Clang: `-Wall`. Release: link-time optimization (`INTERPROCEDURAL_OPTIMIZATION_RELEASE`, if `check_ipo_supported` says the compiler can). Keep the build warning-free (Debug and Release). When adding a source file, add it to `VM_SOURCES` in `CMakeLists.txt`.

## C++ status

All sources are `.cpp` and compile as C++20, and both the **compiler** and the **VM** (all in `src/`) are organized in classes (see Layout); their method bodies are still mostly the original C code (`printf`, `malloc`/`calloc` with casts). There is no reference image: after a compiler or VM change, check that the unit tests still pass (see Tests), not that an image is byte-identical. In the compiler, lists are `std::vector` and names are `std::string` (no fixed `MAX_...` buffers, no `strdup`); only `Parser`'s text and token buffers are still `char` arrays, because `fgets` fills them and the `char*` `cursor` moves through them; they stay private to `Parser`. Pass names on to the C-style code with `.c_str()`. In a `.cpp` file the functions are in the order they are normally called (each one after its first caller, depth first; error paths last), with the destructor right below the constructor(s). In the class headers the data members come first (constants a member array needs, like `Parser::inputBufferSize`, before them), then the functions; **All class member function bodies go in the `.cpp` files**, in the VM as well as the compiler, even one-line accessors on the interpreter's hot path (`Object::size()`, `SmallInt::value()`, `ObjectMemory::allocate()`, `MethodCache::find()`...); headers only declare them (`= default`/`= delete` aside, and templates, which must be in the header: only `Log::error`). Without link-time optimization the compiler cannot inline them into the interpreter loop (a benchmark ran about 40% slower); that is why Release builds use link-time optimization, which makes it as fast as with the bodies in the headers. Debug builds are not optimized anyway.

Things C++ requires that are already done; keep them that way:
- No identifiers named after C++ keywords: a name that would be a keyword gets an underscore in front (locals and parameters `_class`, not `class` or `cls`); the object header field is `objectClass`.
- String literals are `const char *`; functions that only read a string take `const char *`.
- `void *` from `malloc`/`calloc` is cast explicitly, e.g. `(char *)malloc(n)`.
- No `register`.
- The object structs end in a flexible array member (`data[]`, `bytes[]`). C++ accepts it as an extension (MSVC, GCC, Clang); `Object.h` silences MSVC's C4200 for it.
- Fatal errors are `Log::error(...)`, not a macro (there is no `error` macro any more, so a standard header that uses the name `error` is safe). Pass only plain values to it (numbers, pointers, `const char*`: use `.c_str()`), they go through C varargs. It is the one exception to the bodies-in-`.cpp` rule, because it is a template.

## Windows notes

- Always open files in **binary** mode (`"rb"`/`"wb"`). The image is binary and Smalltalk sources use LF; `CompiledImage::writeImage` writes with `"wb"`, and the file-open primitive (100) appends `b` to the mode Smalltalk passes.
- Don't include `<windows.h>` (or anything that pulls in `winuser.h`, like `<winsock2.h>`): it `#define`s `SendMessage` and many other names (the bytecode is `OpCodes::sendMessage` now, but other names could clash).

## Code style

Local variables are declared at their first use, as late as possible, with their value (`int count = keys->size();`), not at the top of the function: in the innermost block that holds all their uses, a loop variable in its `for`. A variable used for two unrelated things is two variables. They stay earlier only when they must: the value is set in several branches or by an out-parameter (`readTag( file, &type, &value )`), or it is used after the loop that sets it. In a `switch`, a declaration goes inside braces of its own `case` (`case objectType: { int size = value; ... break; }`): a `case` label must not jump over it.

Naming: functions and variables (locals, parameters, globals, members) are **camelCase** (`lstTimeUsec`, `objectWrite`, `gcTotalTime`, `okMissing`); variable names are full words, like in the Smalltalk sources (`object`, `file`, `arguments`, `matchString`, not `obj`, `fp`, `args`, `matchStr`), with one exception: an index is `i`, not `index`, and a name that would be a C++ keyword gets an underscore in front (`_class`); classes and struct types PascalCase (`Object`, `ByteObject`, `MObject`, `MethodCache`, `CompiledClass`), `constexpr` members of classes camelCase like variables (`ObjectMemory::defaultDynamicSize`, `Parser::inputBufferSize`, `Image::objectType`), macros UPPER_CASE; the namespace-level constant `BytesPerWord` keeps its name for now. Use `bool` with `true`/`false` for anything that is a yes/no value (success of a parse function, `is...` tests, flags, the `failed` out-parameter of `Primitives::call`, `CompiledImage::lookupGlobal`'s `okMissing`), not `int` 0/1; keep `int` for counts, indexes, comparison results and status codes (`Interpreter::execute`'s `OpCodes::return...` values). Types with member functions are `class`es, also the object layout types (`class Object`, forward declared as `class Object;`: declaring one type with both keywords gives MSVC warning C4099); `struct` is only for plain data without functions (`MethodCache::Entry`). Write types without the C `struct`/`class` keyword (`Object* object`, `sizeof( Object )`, `timeval now`). A header that uses `Object` without including `Object.h` needs that forward declaration (most headers). No snake_case names, except standard library ones (`size_t`, `int64_t`, `push_back`, `struct timeval`...).


All `*.cpp`/`*.h` files are formatted with clang-format using the project's `.clang-format` (it takes precedence over the shared `../.clang-format` in the parent `Cpp` folder): indentation with tabs only (width 4; `public:`/`private:` at the class's own indentation, so no 2-space indents), `*` and `&` attached to the type (`char* p`, `Parser& parser`), spaces inside parentheses and brackets (`foo( x )`, `v[ i ]`, `if( cond )`), a space after C-style casts (`(int) x`), function and class braces on their own line, other braces K&R, no braces around a single-statement body of `if`/`else`/`for`/`while` (`RemoveBracesLLVM`), no column limit. clang-format leaves declarations of several pointers on one line as they are (`Object *a, *b;`). LF line endings, C-style `/* */` comments.

Smalltalk sources (`*.st`): variable names (arguments, temporaries, block arguments, instance and class variables) are full words in camelCase, no abbreviations or single letters (`index`, `element`, `aNumber`, `fileName`, not `i`, `elem`, `arg`, `nm`); a name must not hide an instance variable (temporaries and arguments win, so the method would silently change meaning; on the class side the `Class` variables `name`, `size`, `variables`... are instance variables too). Indentation with tabs (a method's statements one tab, each block or continuation line one more); comment lines on the top level of a method one tab; the temporaries `| a b |` on their own line below the method header; a space inside parentheses and brackets (`( a + b )`, `[ :x | x * 2 ]`, also around the `|` after block arguments) when the expression is on the same line; the closing bracket of a block is not on a line of its own (it ends the line of the block's last statement: `^ self add: elem ].`); the last statement of a method ends with a period, and there are no empty lines before the closing `!`. After a reformat, the unit tests must still pass.

- Reformat after editing, with the clang-format bundled with VS (not on PATH), and **keep include sorting off** (the include order is deliberate: standard headers first, then the project headers):
  ```
  "C:/Program Files/Microsoft Visual Studio/18/Community/VC/Tools/Llvm/x64/bin/clang-format.exe" -i --sort-includes=false src/*.cpp src/*.h
  ```
  (`src/version.h` is generated; formatting it is harmless but pointless.)
- `CMakeLists.txt`, `CMakePresets.json`, `cmake/*.cmake` use tabs.

## Tests

The unit tests of the system classes are in `Smalltalk/Test`: `bin\lst.exe -o bin\test.img Smalltalk\System Smalltalk\Test`, then `bin\lst.exe bin\test.img` (or the launch config). They run from any folder: a test must not depend on the current folder (`TestFile` reads the image it runs in: the last command line argument, else `lst.img`). After a change:
- The build must bootstrap the image `bin/lst.img` ("2161 objects written").
- **All unit tests must pass** (`All N tests passed`). This is the check for compiler, VM and system class changes, and for reformats; images are not compared byte for byte.
- REPL: `echo (3 + 4) printNl | bin\lst.exe bin\lst.img` should print `7`; the examples should still run (their `build.sh` and `start.sh`).
- For VM changes, also run the unit tests with tiny start sizes (set `ObjectMemory::defaultStaticSize` to 100 temporarily, so `lst -o` needs many static blocks; and `ObjectMemory::defaultDynamicSize` to 2000: thousands of garbage collections, the space grows many times, and loading an image has to reserve room first) and compare the output with the old VM (the VM prints no statistics at exit any more: the counters are still in `ObjectMemory` and `MethodCache`, so print them temporarily to compare the garbage collection count); and check that an image written with `File image: 'x.img'` loads and runs.
